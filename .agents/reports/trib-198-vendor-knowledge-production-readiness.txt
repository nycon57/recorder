## Flow Evidence

### Recording and Extension Upload

Status: PASS.

The upload-init route validates writer permission, file type, file size, duration,
source metadata, and extension idempotency before creating content in
`SOURCE_STATUS.UPLOADING` and returning current content-bucket storage paths.
Metadata submission validates ownership/admin access, checks the uploaded object,
persists user metadata, and enqueues the first processing job with a per-content
dedupe key. Finalize also validates org ownership and storage path contracts,
including the legacy recordings bucket fallback, then enqueues `transcribe`.

Worker dispatch covers `transcribe`, `extract_audio`, `doc_generate`,
`generate_embeddings`, `compile_wiki`, and vendor ingestion. The current
production worker imports Gemini transcription, Google document generation, and
Google embeddings handlers. `docify-google` is idempotent when a document already
exists, enqueues missing embeddings, and enqueues compile-wiki unless workflow
extraction owns the compile step. `embeddings-google` checks for complete or
partial chunks before generating embeddings and writes `transcript_chunks`.

Focused evidence:

- Recording metadata/finalize tests passed.
- Worker processor tests passed.
- `npm run verify:knowledge-readiness` passed all first-party content,
  transcript, document, wiki, source-link, relationship, recall-citation, and
  atomic-contract checks.

Residual risk:

- Provider-backed transcription, document generation, embeddings, FFmpeg, and
  storage operations were verified through code path and mocked/focused suites,
  not through a live provider E2E run in this worktree.
- `type:check` remains baseline-red in worker files, including some active
  transcription/embedding handlers. The focused suites prove behavior but do not
  remove the repo-wide typing advisory.

### Legacy Finalize Path

Status: PASS.

The legacy finalize route is not removed; it is explicitly retained as a
compatibility path. If no storage path is supplied, finalize builds the legacy
recordings-bucket path and validates it with `allowLegacyRecordingsBucket: true`.
If a caller supplies a path, the route infers and validates the storage bucket
against the content/recording contract before writing `storage_path_raw`.

The legacy recall question is separate from upload finalize. `npm run
verify:legacy-recall-quarantine` passed 13/13, proving production answer
surfaces such as extension query and MCP use canonical compiled-memory recall
rather than legacy RAG/vector modules.

Residual risk:

- The compatibility finalize path should remain documented until clients no
  longer submit legacy bucket paths.

### Library Upload

Status: PASS.

The library upload route requires writer permission, enforces `Content-Length`
before multipart parsing, applies aggregate upload limits, rejects recording
content that belongs in the recording endpoint, stores accepted content in the
content bucket, and enqueues the first processing job based on content/file type.

Text uploads create a transcript immediately and enqueue `process_text_note`.
Direct text creation writes content plus a user-input transcript and enqueues
`doc_generate`. WebM/video uploads enqueue `extract_audio`, which writes MP3
derived audio as `audio/mpeg` and enqueues `transcribe`. Document uploads route
through PDF/DOCX extraction handlers before document generation and embeddings.

Focused evidence:

- Library upload/text tests passed 12/12.
- Test output includes expected negative-path logging for reader denial,
  content-length rejection, aggregate-size rejection, transcript rollback, and
  storage/signed-url failure handling.

Residual risk:

- Full live WebM/FFmpeg extraction was not executed in this verification pass.
  The code path and tests cover routing and payload shape.

### Google Drive Import

Status: PASS.

The Google Drive import route resolves the connector, tests connection, avoids
duplicate imports via `source_external_id`, stores source tracking on `content`,
writes `connector_sync_state`, and then branches:

- Text-like Drive files create transcripts with `provider:
  google_drive_import` and enqueue `doc_generate`.
- Binary PDFs/DOCX files upload raw bytes to storage and enqueue the matching
  extraction job.
- Unsupported types fail before content creation or are rolled back.

`process-imported-doc` covers the older imported-documents path by chunking
connector content semantically, embedding chunks, and storing them in
`transcript_chunks` with connector/import metadata for recall.

Focused evidence:

- Google Drive import tests passed 7/7, including text import, PDF import,
  duplicate/job failure rollback, and unsupported binary rejection.

Residual risk:

- The current Google Drive route writes through unified content jobs, while
  `process-imported-doc` still references `imported_documents`. That is not a
  blocking defect for the tested route, but it is an architectural advisory to
  keep the older connector path either migrated or quarantined.

### Vendor Source Sync and Corpus

Status: PASS.

Vendor source registration normalizes HTTPS URLs, requires official vendor host
ownership, stores fetch strategy, freshness, lifecycle, terms/legal review, and
official-source status. Queryability requires active lifecycle, approved terms,
and official source. Sync scheduling creates `ingest_vendor_docs` jobs with
source-scoped dedupe keys, freshness/backoff checks, adapter support checks, and
optional `triggered_by_user_id` provenance.

The ingestion handler builds a source acquisition plan from the registered
source, rejects unsupported fetch strategies, enforces publisher-host scope,
fetches and respects robots.txt, limits crawling to the same host and source
path prefix, hashes page content, upserts page rows, retires stale rows, and
syncs normalized `vendor_corpus_pages` with embeddings. Corpus retrieval syncs
from legacy pages, filters queryable source rows, ranks by semantic similarity,
keyword score, and exact screen match, then returns page/source identities.

Focused evidence:

- Vendor registry/sync/ops/corpus tests passed 20/20.
- Worker vendor-doc upsert tests passed.

Residual risk:

- This verification does not make a live crawl against third-party vendor
  sites. Legal/robots readiness is verified by code path and tests, not by
  external crawl execution.

### Extension Context, Live Context, and Query

Status: PASS.

`/api/extension/context` accepts session auth or API-key auth, sanitizes page
context, resolves app/screen, requires `customerOrgId` for API-key recall,
verifies that the requested customer org belongs to the vendor org, and resolves
extension context matches. It returns vendor/org knowledge matches,
availability, relevant wiki pages, and telemetry.

`/api/extension/live-context` refreshes stale context matches when the page
signature changes, loads the matched org and vendor pages, filters vendor pages
through queryability, and builds a live context pack.

`/api/extension/query` uses canonical compiled-memory answer context. It accepts
context-match page ids, resolves customer org scope for API-key calls, streams
answer chunks, element references, citations, and done events, and records
telemetry.

Focused evidence:

- Extension context/live-context/query and SDK query-client tests passed 26/26.
- Legacy recall quarantine confirms extension query uses canonical recall.

Residual risk:

- Live browser extension behavior was not exercised here. The endpoint and SDK
  contract are covered by focused tests.

### SDK, API Keys, and Customer Scoping

Status: PASS.

The SDK requires both `apiKey` and `customerOrgId`. SDK init sends the API key in
Authorization and the customer selector in `X-Tribora-Customer-Org-Id`; query
sends `customerOrgId` in the request body. Server routes require API-key callers
to provide a customer org and call `resolveCustomerOrgForVendor`, which rejects
self-targeting, deleted orgs, and orgs not linked to the vendor.

Vendor API keys are generated as one-time plaintext keys, stored hashed, scoped
to a white-label config, and rejected if inactive or revoked.

Focused evidence:

- SDK query-client tests passed.
- Extension route tests passed API-key customer scoping scenarios.

Residual risk:

- `src/lib/utils/api-key-validation.ts` has baseline TypeScript advisories in
  the full typecheck. Focused SDK/extension tests pass.

### MCP

Status: PASS.

`/api/mcp` accepts GET/POST/DELETE with Bearer API keys, returns JSON-RPC
errors for missing/invalid auth, and serves MCP over the web-standard streamable
HTTP transport. MCP auth validates dedicated `trb_mcp_` keys or legacy
`sk_live_` keys, scopes all handlers by `orgId`, rate-limits per key when Redis
is available, and updates request counts.

MCP handlers answer questions through compiled-memory context, return citations,
search compiled org wiki pages, search vendor wiki pages, and fetch org/vendor
wiki pages. Vendor search stays separated from org-scoped compiled memory while
still returning through the same tool surface.

Focused evidence:

- MCP route and handler tests passed 10/10.
- Legacy recall quarantine confirms MCP handlers use canonical compiled/wiki
  recall and registered legacy allowlists only where documented.

Residual risk:

- No external MCP client smoke was run in this worktree; connectivity is covered
  at route/handler level.
